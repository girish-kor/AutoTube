# ANALYTICS — Metrics, Storage & Feedback Loop

## 1. Metrics Collected

Pulled daily by `17-Analytics-Collector` (`N8N_NODES.md`) via YouTube Analytics API, stored in `analytics_daily` (`DATABASE.md` §11):

| Metric | Source field | Used for |
|---|---|---|
| `views` | `views` | Reach signal |
| `watch_time_minutes` | `estimatedMinutesWatched` | Core ranking-correlated signal |
| `avg_view_duration_seconds` | `averageViewDuration` | Retention/content-quality signal, especially for Shorts (§4) |
| `likes`, `comments` | `likes`, `comments` | Engagement signal |
| `ctr` | derived: impressions-based CTR requires the `card_impressions`/`impressions` metric where available via Analytics API; where unavailable at video-level for the account tier, approximated via `views`/known impression proxies — recorded as `null` when not obtainable rather than fabricated | Title/thumbnail effectiveness |
| `subscribers_gained` | `subscribersGained` | Channel-growth attribution per video |

Distinct rows per `(video_id, is_short, metric_date)` — long-form and Shorts tracked identically but separately, since Shorts retention curves (§4) are interpreted differently.

## 2. Pipeline Observability (operational, not audience, metrics)

Separate from audience analytics — operational health is tracked via:

| Signal | Source | Surfaced via |
|---|---|---|
| Stage durations | `videos.updated_at` deltas between consecutive stage transitions | Ad-hoc SQL against `videos`; flagged in weekly summary if any stage's median duration regresses >2x |
| Error rate | `pipeline_errors` count per workflow per day | Telegram alert on any `FAILED` (immediate, `ERROR_HANDLING.md`); weekly digest of resolved-but-retried errors |
| API quota headroom | `api_usage` vs `unit_limit` per API per day | Pre-flight checks (`YOUTUBE_API.md` §3); logged, alertable if consistently >80% utilized |
| Throughput | Count of `videos` reaching `PUBLISHED`/`SHORTS_PUBLISHED` per day vs. `channels.daily_*_quota` | Weekly summary — under-throughput signals a stuck stage worth investigating |

n8n's own built-in execution log (retained per `EXECUTIONS_DATA_MAX_AGE`, `CONFIG.md`) provides node-level tracing for any individual run without a separate observability stack — sufficient at this scale, avoiding a paid APM tool.

## 3. Weekly Summary (sent via Telegram, generated by a lightweight extension of `18-Optimization-Loop`)

Plain-text digest: videos published, total views/watch-time delta week-over-week, top-3 and bottom-3 performing videos by CTR, error count, quota utilization — gives the operator a five-second health check without opening n8n or Postgres directly.

## 4. Shorts-Specific Interpretation

Shorts retention is read as `avg_view_duration_seconds / clip_length_seconds` (a completion-rate ratio), not absolute watch time — this ratio feeds directly into `AI_PIPELINE.md` §7's highlight-scoring weight tuning (clips whose extraction window scored well on the heuristic but completed poorly get that scoring pattern down-weighted).

## 5. Feedback Loop (full detail in `AI_PIPELINE.md` §8, `SEO.md` §9)

```
analytics_daily (≥7 days data)
        │
        ▼
18-Optimization-Loop (weekly)
        │
        ├─► config.topic_scoring_weights   → influences 02-Topic-Selection
        ├─► config.seo_prompt_examples      → influences 11-SEO-Metadata
        └─► config.shorts_scoring_weights   → influences 14-Shorts-Extraction
```

This is the system's only place where past performance changes future automated decisions — kept centralized in one workflow so the feedback logic is auditable in one place rather than scattered per-stage heuristics silently drifting.

## 6. No Paid BI Tooling

All analytics live in Postgres, queryable directly via `psql`/any free SQL client (DBeaver, free) or a free self-hosted Metabase/Grafana instance if the operator wants dashboards (optional add-on container, not required for pipeline function) — no paid analytics SaaS (e.g., paid Looker/Tableau tiers) is part of the required stack.
